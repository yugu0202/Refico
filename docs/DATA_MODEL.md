# サーバー版のデータ構造

## 所有範囲

本番はGoogleアカウントをBetter Authで認証する。プレビューはCloudflareが認証済みのctx.accessからAccessユーザーを取得し、Googleログインを省く。Accessのuser_uuidから専用ユーザーIDを生成する。認証情報がない場合は拒否する。データの所有者はユーザーではなく家庭（households）。初回ログインで専用の家庭とowner所属を同一トランザクションで作る。今回は個人用で、招待・家庭切替APIは提供しない。将来はhousehold_membersへの所属を追加する。全レコードの主キーと外部キーにhousehold_idを含め、他の家庭への参照をDBでも拒否する。

APIの家庭は認証済みユーザーの所属から決める。リクエストで家庭IDや所有者を指定できない。

## 記録

| テーブル           | 内容                                                   |
| ------------------ | ------------------------------------------------------ |
| products / units   | 食材・独自単位。単位にはIDと表示順を持つ               |
| purchases          | 実際の購入。購入日・元の数量・単位・換算係数・価格     |
| lots               | 購入または在庫増加による在庫ロット。数量・原価・発生元 |
| cookings / batches | 調理と作り置き。材料消費と作成食数・調理原価           |
| meals              | 食べた日と食事種別。調理しただけでは作成しない         |
| usages             | 食事または調理で使った食材と当時の換算情報             |
| portions           | 食事で食べた作り置き。作成時に食べた分も同じ形式       |
| allocations        | 食材使用・在庫減少とロットの数量・原価配分             |
| adjustments        | 食材の実測在庫調整。増加は独立ロットを作成             |
| discards           | 作り置きの廃棄による残量・原価の減少                   |
| mutation_receipts  | 重複送信防止と更新リビジョン・実行者                   |

各レコードは独立した行に置く。型付きデータはJSON列、参照列は生成列と複合外部キーで保持する。購入/ロット、調理/バッチの相互参照は遅延外部キーで同じトランザクション内に作成する。

数量は基準単位の1/1000整数、作り置きの食数も1/1000整数、金額は円整数。各記録のsequenceはサーバーが家庭内で採番し、日付とは別に登録順を保持する。名前や単位設定の編集では過去の換算・原価を変更しない。

作り置きの増加調整は作成食数の訂正としてバッチを更新し、関連する食事と廃棄原価を再計算する。食材使用原価の総額は維持する。減少は廃棄記録で、食費には含めない。廃棄記録の実測残量を満たせなくなる履歴訂正は拒否する。

## APIと更新

- `GET /api/bootstrap`: 認証ユーザー、家庭、リビジョン、画面・計算用データ。
- `POST /api/commands`: `{ requestId, revision, command }`。
- コマンドは食材登録・編集、購入登録・編集、食事/調理登録・編集、在庫調整、作り置き名変更、サンプル追加。
- 原価・配分・正規化済み数量をクライアントから受け取らない。入力形式を検証し、サーバーで換算・配分・再計算する。
- サーバーは既存リビジョンから結果を計算し、更新対象行の差分と送信記録をD1のbatchで原子的に保存する。
- 送信記録のトリガーでリビジョンと所属を検証する。競合時はbatch全体をロールバックし409を返す。
- 同じrequestId・入力・元リビジョンの再送は再実行せず、現在の保存結果を返す。同じIDで異なる入力は409。
- 保存応答を失った場合、クライアントは同じIDで再送する。明示的な409では最新データを読み込み、フォームを保持して再確認を促す。
- セッション切れは401。本番の書込みは設定済み公開URL、Accessプレビューではアクセス中のWorker URLと同じOriginからのみ受け付ける。

## 計算・画面の投影

`src/domain/model.ts`が永続モデルと`State`の投影を変換する。既存の検証済みFIFO・累積丸め・履歴再計算を引き続き使用するため、計算と画面の投影では従来の配列構成を使う。配列位置（mealCount / purchaseCount）はsequenceから都度導出し、DBには保存しない。調理記録とその場の食事をフォームでは一度に入力できる。

localStorageによる在庫保存と旧データ互換処理は撤去した。旧ブラウザデータを読んだり移行したりしない。

## 今回の範囲と今後

初版のbootstrapは家庭全体の計算投影を取得する。履歴の20件切替はクライアント上のページングで、サーバーページングではない。原価プレビューは端末上で計算し、保存時はサーバーが再検証・確定する。データが増えた場合には在庫残量の投影とプレビューAPIを追加し、履歴・月別食費の取得を分割する。

履歴編集時は家庭内の記録を再計算するが、DBへの書込みは変更された行のみ。認証済みセッションとGoogle OAuthの実環境検証にはOAuthクライアント設定が必要。招待と家庭切替、オフライン書込み、記録削除は今回の範囲外。
